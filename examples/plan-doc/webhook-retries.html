Webhook retries

About 1 in 200 paid orders never gets a ticket because the payment webhook fails once and nothing tries again. This plan retries it in the background until the ticket is issued or a person is paged.

recommendation

Move ticket issuing out of the webhook handler into a Celery task that retries 5 times over about 30 minutes, keyed on payment_id so a retry can never issue a second ticket. Ship it in one PR behind a flag.

Needs from you: approve the new webhook_events collection and the Slack alert channel.

What happens when this ships

  • A fan who pays gets their ticket even if Mongo or the email worker blips during checkout.
  • The webhook answers Razorpay in under 200 ms instead of up to 4 s, so Razorpay stops retrying on its side.
  • If all 5 retries fail, #payments-alerts gets the order id. Support no longer finds these from angry emails.
  • Nothing changes for fans whose payments already work.

Steps

  1. Make issuing idempotent. Reuse issue_ticket; add a unique index on payment_id and return the existing ticket on a duplicate key error.

    app/tickets/service.py, migrations/0042_webhook_events.py

  2. Add the task. New Celery task wraps issue_ticket with autoretry_for, backoff starting at 30 s, max 5 tries.

    app/payments/tasks.py

  3. Slim the handler. Keep the existing signature check, write the event, enqueue the task, return 200. Old inline code stays behind the flag.

    app/payments/webhooks.py

  4. Alert on final failure. On the last retry, post order id and error to Slack using the existing notify_slack helper.

    app/payments/tasks.py

  5. Test, deploy, flip the flag. Deploy with the flag off, turn it on for one event, then for all.

    tests/payments/test_webhook_retry.py

Decisions

Retry in Celery, not in the handler easy to undo

Razorpay expects a response within 5 seconds. A Celery task can back off for half an hour without holding a request open.

Considered: retrying inline (blocks the response), relying on Razorpay's own retries (they stop after 24 hours and give no alert).

Dedupe on payment_id hard to undo

One payment, one ticket. A unique index makes the second write fail instead of trusting every caller to check first.

Considered: dedupe on order id (one order can have two payment attempts).

Risks

risklevelwhat we do about it
Index build locks the tickets collectionmediumBuild in the background at 4 am IST; 180k documents takes under a minute in staging.
Celery backlog delays tickets during a big on-salelowTask goes on the existing high-priority queue.

Out of scope

  • Retrying failed refunds. Same pattern, separate PR.
  • A support dashboard for stuck orders. The Slack alert covers it for now.

Open questions

  1. Should the fan get an email when their ticket arrives late?

    Recommended: no. The normal ticket email already goes out when the task succeeds.

  2. Which Slack channel gets the alert?

    Recommended: a new #payments-alerts, so it isn't lost in #eng.
